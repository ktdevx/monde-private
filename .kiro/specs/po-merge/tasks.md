# Implementation Plan

- [ ] 1. po_merge モジュールの基盤
- [ ] 1.1 po_merge モジュールとテスト実行ファイルの雛形を作り、構成・ビルド・テストの手順を通す
  - 設計の公開ヘッダ（設定・統計の型とマージの関数）と内部ヘッダ（Builder、Header、KeyIndex、Fuzzy、Similarity、Hash の型と関数）を置き、設計の宣言をすべて書く
  - 内部ヘッダでは、Hash、KeyIndex、Fuzzy、Similarity の構造体の定義（フィールド）もここで確定させる。Fuzzy は候補の添字の列、4-gram の表と添字の列、バイト長ごとの列、作業領域（数え上げの配列、触れた候補の列、問い合わせのマスク）を、Similarity はマスクの語数と 256 種のマスクを持つ。内部ヘッダは部品ごとの節に分け、以降のタスクで構造体を変える必要が出た場合は、そのタスクの部品の節だけを編集する
  - 設計の File Structure Plan の製品のソース 7 つ（手順、エントリの組み立て、ヘッダ、索引、あいまい一致、類似度、ハッシュ表）を最初から登録する。各ソースは空の翻訳単位にならず、警告なしでコンパイルできるようにする。公開のマージの関数は、実装されるまで「出力を空にして false を返す」仮の実装にしておく
  - モジュールは po と foundation だけに依存する。`src/` と `tests/` のビルドファイルにモジュールを追加する（po の後）
  - テスト実行ファイルを、7 スイート（similarity、index、entry、fuzzy、header、merge、golden）を登録するエントリポイントと、スイートごとに 1 つのテストファイルで作る。各スイートに雛形のテストを 1 件置く。テストデータのディレクトリをコンパイル定義で渡す
  - steering（structure.md）の予約済みの短縮名に、po-merge の `merge` を追記する
  - ソースとテストファイルの登録はここで完了させる。以降のタスクは、自分が担当するソースとテストファイルだけを編集すれば済むようにする。例外は 1.2（テスト用の補助）と、検証タスクの 5.2・5.3（互換性テストと性能テストの登録）である
  - 完了時: 標準の 3 行の手順が成功し、CTest に `po_merge_tests.<suite>.<test>` 形式のテストが 7 スイート分表示され、`ctest -L po_merge` で実行できる。`BUILD_TESTING=OFF` でも `monde_po_merge` がビルドできる
  - _Requirements: 11.1, 11.2_

- [ ] 1.2 テスト用の補助関数を作る
  - PO の文字列からカタログを作る（読み込みに失敗したらテストを失敗させる）、カタログを既定の設定で書き出して期待する文字列とバイト単位で比べる（差があれば両方を表示する）、テストデータのディレクトリのファイルを読み込む、の 3 つを用意する
  - 補助関数はテストのソースとしてテスト実行ファイルに登録し、製品のライブラリには含めない
  - 完了時: 補助関数を使った雛形のテスト（短い PO を読み込んで書き出すと元に戻る）が merge スイートで合格する
  - _Requirements: 11.2_

- [ ] 1.3 バイト列をキーとするハッシュ表を実装し、単体テストを書く
  - 設計の Hash のとおり、開番地法（FNV-1a、容量は 2 の累乗、使用率 1/2 以下）で挿入と検索を実装する。キーは複製せず、呼び出し側の領域を指す
  - 既にあるキーの挿入では値を変えずに既存の値を返す。容量の拡大と確保の計算は、確保の前にオーバーフローを検査する
  - 完了時: index スイートで、挿入と検索、既存のキーの挿入で先の値が残ること、容量の拡大の前後で全キーの値が保たれること、長さ 0 のキー、のテストが合格する
  - _Requirements: 10.1_

- [ ] 2. 各段階の部品
- [ ] 2.1 (P) 類似度の計算（LCS、上限、比較値）を実装し、単体テストを書く
  - 問い合わせの文字列から 256 種のバイトの位置のビットマスク（64 ビットの語の列）を作り、候補の文字列の各バイトで更新する bit-parallel LCS を実装する。語の列の加減算は桁上がり・桁借りを伝える
  - 比較値の分数 `(double)(2 × LCS) / (double)(長さの和)`（長さの和が 0 なら 1.0）と、長さによる上限・バイトの出現数の差による上限（長さの和が 20 以上）の分子を、設計と同じ形で計算する。数学関数のライブラリは使わない
  - 完了時: similarity スイートで、空と空・片方だけ空・同一・共通なし・UTF-8 の複数バイト文字、64 バイト・65 バイト・128 バイトを超える問い合わせのテストと、固定の種の擬似乱数による 1,000 組でテスト内の動的計画法の LCS と一致すること、上限の分子が常に `2 × LCS` 以上であることのテストが合格する
  - _Boundary: Similarity_
  - _Requirements: 3.2, 10.2_

- [ ] 2.2 (P) msgctxt と msgid による索引と、重複の検出を実装し、単体テストを書く
  - キーを「msgctxt の有無の 1 バイト + msgctxt + 区切り + msgid」の連結として索引が所有し、ハッシュ表でカタログの添字を引く
  - 登録済みのキーは上書きせず、先に登録された添字を返す。登録の順で、通常のエントリの優先と、先の廃止エントリの優先を表せるようにする
  - 完了時: index スイートで、msgctxt のないキーと空の msgctxt のキーの区別、同じキーの 2 回目の登録で先の添字が返ること、存在しないキーの検索、のテストが合格する
  - _Boundary: KeyIndex_
  - _Requirements: 2.1, 2.6, 2.7, 8.1, 8.2_

- [ ] 2.3 (P) ヘッダのマージと nplurals の読み取りを実装し、単体テストを書く
  - 設計の「ヘッダの規則」の手順 1〜5（行に分ける、既知の 10 項目の取り出し、Language の補完、テンプレートの Report-Msgid-Bugs-To と POT-Creation-Date による置き換え、表の順と綴りでの並べ替え）で msgstr を作る
  - ヘッダのエントリの翻訳者コメント・fuzzy は既存のヘッダから、抽出コメント・参照・fuzzy 以外のフラグはテンプレートのヘッダから取り、前回の msgid は付けない
  - Plural-Forms の `nplurals` を設計の規則で読み、1〜100 以外は 2 を返す
  - 完了時: header スイートで、並べ替えと綴りの統一、未知の行の順序、同じ項目の後の行の優先、末尾に改行のない msgstr、空の msgstr、置き換えと保持と追加、空の Language の補完、翻訳者コメント・fuzzy の保持、テンプレートのヘッダがない場合、nplurals の 6 通りの入力のテストが合格する
  - _Boundary: Header_
  - _Requirements: 5.1, 5.2, 5.3, 5.4, 5.5, 5.6, 6.2, 6.6_

- [ ] 2.4 (P) エントリの複製と組み立て（完全一致・あいまい一致・新規・廃止）を実装し、単体テストを書く
  - エントリの全要素の深い複製を、po-format の公開の関数だけで実装する。失敗時は複製先を初期状態に戻す
  - 設計の手順 5 の表のとおり、既存とテンプレートのエントリから要素を取り、fuzzy の判定（既存の fuzzy、強制、複数形の食い違い）、フラグの順序（`fuzzy` を先頭、テンプレートのフラグを順に）、前回の msgid の 2 通りを実装する
  - 複数形の後処理（単数形 → 複数形で nplurals 個に複製、複数形 → 単数形で最初の msgstr だけ、両方が複数形ならそのまま）、新規の複数形の msgstr[n] の個数、廃止エントリの複製（抽出コメントと参照を消す）、前回の msgid の整理、「訳がある」の判定を実装する
  - 完了時: entry スイートで、要素の取り方、未知のフラグの保持、フラグの順序、前回の msgid の 2 通り、複数形の 3 通りと新規の複数形、廃止エントリの複製、前回の msgid の整理、複製が入力と領域を共有しないこと（入力を変えても結果が変わらない）、のテストが合格する
  - _Boundary: Builder_
  - _Requirements: 1.5, 2.1, 2.2, 2.3, 2.4, 2.5, 2.8, 3.5, 3.6, 3.9, 4.2, 6.1, 6.2, 6.3, 6.4, 6.5, 6.6, 6.7_

- [ ] 3. あいまい一致の候補の選択
- [ ] 3.1 候補の登録と 4-gram の索引を実装する
  - 既存のカタログの訳のあるエントリ（廃止エントリを含み、ヘッダを除く）を添字の昇順に登録する
  - msgid が 4 文字（UTF-8 の文字）以上の候補について、各位置から始まる 4 文字のバイト列ごとに、候補の添字の列（昇順、重複なし）を作る。msgid のバイト長が 28 以下の候補を、バイト長ごとの列に加える
  - テストは内部ヘッダで公開された構造体のフィールド（4-gram の表、バイト長ごとの列）を直接調べてよい
  - 完了時: fuzzy スイートで、未翻訳とヘッダが登録されず廃止エントリが登録されること、同じ 4-gram を 2 回含む候補が列に 1 回だけ入ること、3 文字の日本語（9 バイト）の msgid が 4-gram の索引に入らず長さの列に入ること、のテストが合格する
  - _Depends: 1.3_
  - _Requirements: 3.1, 3.3, 3.8_

- [ ] 3.2 候補を調べる順序と、最良の候補の選択を実装する
  - 4 文字以上の問い合わせでは、問い合わせの 4-gram の各出現で候補を数え上げ、数え上げの降順・添字の昇順（全順序）に並べる。4 文字未満の問い合わせでは、設計の式で求めたバイト長の範囲の列を、長さの昇順・添字の昇順に並べる
  - 比較値に bonus（msgctxt のない候補、または同じ msgctxt の候補で 0.00001）を加え、`volatile` の double で計算する。最良値 0.6 から始めて、最良値を超えた候補だけで更新する
  - 上限による枝刈りは、上限に bonus を加えた値が最良値以下の候補だけを飛ばす。数え上げの配列、触れた候補の列、問い合わせのマスクは作業領域として再利用し、検索の結果に影響させない
  - 完了時: fuzzy スイートで、類似度 0.6 ちょうどの候補を選ばないこと、4-gram を共有しない候補を選ばないこと、同点で数え上げの多い候補が勝つこと、数え上げも同じなら先の候補が勝つこと、4 文字未満の問い合わせで範囲外の長さの候補を調べないこと、msgctxt による bonus の優先、同じ検索を 2 回行うと同じ結果になること、のテストが合格する
  - _Depends: 2.1_
  - _Requirements: 3.1, 3.2, 3.3, 3.4, 3.11, 10.2_
