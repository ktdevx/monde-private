# Requirements Document

## Project Description (Input)
### Problem
Monde の中核は 2 つの処理である。1 つは、Markdown とフロントマターから翻訳単位（msgid）を抽出すること。もう 1 つは、翻訳ファイルの訳文を原文の正しい位置に差し戻して、翻訳済み Markdown を作ることである。この 2 つの処理は対になっている。抽出の規則と差し戻しの規則が食い違うと、ラウンドトリップが成立せず、書式も壊れる。

### Current State
この処理はまだない。markdown-parser、yaml-front-matter、po-format が部品として提供される予定である。

### Desired Outcome
- 原文から、ブロック単位の翻訳単位の列（msgid、参照 `#: file.md:行番号`、要素の種類を示す `#.`）を生成できる。重複する msgid は 1 つにまとめる。
- 原文と翻訳の対応表から、翻訳対象の範囲だけを置き換えた Markdown を生成できる。
- 翻訳がない場合は、原文とバイト単位で同じ出力になる。

### Approach
- 抽出と差し戻しは、共通の「翻訳セグメント」モデルの上に構築する。セグメントは、構文木やフロントマターから取り出した、原文範囲と論理テキストの組である。
- 抽出では、セグメントの論理テキストを msgid にする。複数行のブロックでは、行頭のプレフィックスを除いて正規化する。
- 差し戻しでは、訳文を原文の範囲に戻す。複数行の場合は、各行のプレフィックス（引用の `>`、リストのインデントなど）を復元する。

### Scope
- **In**:
  - 翻訳対象の判定: 見出し、段落、リスト項目内の段落、引用内の段落、画像の alt、指定したフロントマターのキー
  - 翻訳対象外の判定: コードブロック、HTML ブロック、URL
  - msgid の正規化（インライン記法を含める、行頭のプレフィックスを除く、改行の扱い）
  - 重複の統合、参照コメントと要素の種類を示すコメントの生成
  - 訳文の差し戻しと、プレフィックス・改行コード（LF / CRLF）の復元
  - 未翻訳・fuzzy のエントリは原文を使う（fuzzy を採用するかは呼び出し側が指定する）
  - 翻訳率の集計に必要な情報の提供
- **Out**:
  - ファイルの入出力と CLI（monde-cli）
  - PO の書式とマージ（po-format、po-merge）
  - Markdown と YAML の構文解析そのもの

### Boundary Candidates
- 翻訳セグメントのモデル
- 抽出器（構文木とフロントマター → セグメント → PO エントリ）
- 再構成器（原文 + 訳文の対応表 → 出力バイト列）

### Out of Boundary
- 同一文を分けて翻訳するオプション（将来の拡張。msgctxt を使えるようにセグメントの識別を設計しておく）
- GFM の表のセルなど、方言固有の翻訳単位（次の版）

### Upstream / Downstream
- **Upstream**: po-format、markdown-parser、yaml-front-matter
- **Downstream**: monde-cli

### Existing Spec Touchpoints
- **Extends**: なし
- **Adjacent**: markdown-parser（ソース範囲の表現）、yaml-front-matter（値の書き戻しの整形）

### Constraints
- 翻訳対象以外は原文をバイト単位で保持する（Q4-1）。
- インライン記法は msgid に含める（Q2-1）。一方で、URL は翻訳対象外、画像の alt は翻訳対象とする（Q2-2）。この 2 つをどう両立するかは要件で確定する。候補は、URL を msgid にそのまま残す案と、プレースホルダにする案、alt を別の msgid にする案である。
- 訳文に改行や Markdown として意味を持つ文字が含まれていても、ブロック構造が壊れないようにする方針を、設計時に決める。
- yaml-front-matter の部品の前提（yaml-front-matter の design.md の「改訂」の節を参照）:
  - 整形の出力は範囲にそのまま挿入する。空の範囲（`key:`、`{k}`）への出力は区切り（`" "` または `": "`）から始まるので、区切りを自分で付けない。
  - ブロックスカラーの範囲は、内容の行があればヘッダの行のコメントを含む。
  - `end_line` は `span.end` の位置の行（markdown-parser の `span.end - 1` の行と意味が違う）。
  - フロントマターの検出結果は行番号を持たない。参照コメントの行番号は `mnd_source_line_of` で求める。
  - キーパスの照合の結果は文書の確保関数から確保されるので、`mnd_yaml_matches_free` を `mnd_yaml_doc_free` より前に呼ぶ。

## Introduction
translation-units は、Monde の中核となる 2 つの処理を担う部品である。1 つは、Markdown 本文と YAML フロントマターから翻訳単位（msgid）を抽出し、PO のエントリの列（翻訳テンプレートの内容）を作る「抽出」。もう 1 つは、原文と翻訳カタログから、翻訳対象の範囲だけを訳文に置き換えた翻訳済み Markdown を作る「再構成」である。両者は共通の「翻訳セグメント」（原文の範囲と、その論理テキストの組）の上に成り立ち、抽出の規則と差し戻しの規則が常に一致することで、ラウンドトリップと書式のバイト単位の保持を成立させる。利用者は `monde extract` / `monde translate` を実装する monde-cli の開発者で、その先の利用者は翻訳者と文書の保守者である。本部品は markdown-parser、yaml-front-matter、po-format の上に構築され、Monde 固有の知識（何を翻訳対象にするか、msgid をどう作るか）を集約する唯一の場所である。

### 要件確認で決めた挙動
- インライン記法は、リンク先 URL・画像 URL・title を含めてそのまま msgid に含める。画像の alt は `![alt](url)` の一部として msgid に含まれる。URL を別扱い（プレースホルダ化、別 msgid 化）にはしない。「URL は翻訳対象外」は、翻訳者に URL の書き換えを求めないという意味であり、本部品が強制するものではない。
- 複数行のブロックの msgid は、行頭のプレフィックス（`>`、リストのインデントなど）を除いたうえで、行の境界を改行（`\n`）のまま残す。空白 1 つには畳まない。訳文の行数は原文と異なってよい。
- 翻訳率の集計のために、再構成時に文書内の翻訳セグメントの出現ごとに状態（翻訳済み・fuzzy・未翻訳・カタログにない）を数えて返す。率の計算と表示は monde-cli が行う。
- 訳文に空行や行頭のブロック記号など、ブロック構造を変え得る内容が含まれていても、エスケープや除去はせず、警告の診断を返したうえでそのまま出力する。
- フロントマターで指定したキーが存在しないときは診断なしで無視する。値がスカラーでない（マッピングなど）ときは警告して無視する。値が空のときは診断なしで無視する。
- `#.` コメントの語彙は英語で、`heading`（レベル付き）、`paragraph`、`list item`、`block quote`、`front matter`（キーパス付き）とし、入れ子は外側から順に並べる。同じ msgid が異なる種類で出現したら、種類ごとに 1 行にする。
- リンク参照定義（`[label]: url "title"`）は翻訳単位にしない。インラインリンクの title は msgid の一部として含まれる。
- 翻訳がないときの出力が原文とバイト単位で一致することに加えて、msgstr が msgid と同じ内容のときの出力も原文とバイト単位で一致することを必須とする。

## Boundary Context
- **In scope**:
  - 翻訳対象の判定: 見出し（ATX・setext）、段落（リスト項目内・引用内を含む）、画像の alt（段落・見出しの一部として）、指定したキーパスに一致するフロントマターのスカラー値
  - 翻訳対象外の判定: コードブロック（フェンス・インデント）、HTML ブロック、リンク参照定義、区切り線、方言固有のブロック（GFM の表など）そのもの
  - msgid の正規化（インライン記法をそのまま含める、行頭のプレフィックスを除く、改行を `\n` に揃える、末尾の空白の扱い）
  - 同一 msgid の統合、参照コメント（`#:`）と要素の種類のコメント（`#.`）の生成、PO エントリの列の構築
  - 訳文の差し戻しと、行頭のプレフィックス・改行コードの復元、フロントマターの値の書き戻し
  - 未翻訳・fuzzy のエントリの扱い（fuzzy を採用するかは呼び出し側が指定する）
  - 翻訳率の集計に必要な出現ごとの件数の提供
  - 構造を壊し得る訳文に対する警告の診断
- **Out of scope**:
  - ファイルの読み書き、BOM の除去、改行コードの検出、CLI のオプションの解釈、統計の表示（foundation と monde-cli が担う）
  - PO の書式（エスケープ、折り返し、ヘッダ）、`.pot` と `.po` のマージ（po-format と po-merge が担う）
  - Markdown と YAML の構文解析そのもの（markdown-parser と yaml-front-matter が担う）
  - 同一文を文脈ごとに分けて翻訳するオプション（msgctxt の付与）。将来の拡張として、セグメントの出現位置が識別できる形は残す
  - GFM の表のセルなど、方言固有の翻訳単位（次の版）
  - 訳文のエスケープや整形による構造の保護、訳文の Markdown としての妥当性の検査
- **Adjacent expectations**:
  - 入力は、呼び出し側が BOM を除去した UTF-8 のメモリ上のバッファである。原文のバッファは、抽出と再構成の処理の間、呼び出し側が保持する。
  - markdown-parser は、各ブロックのソース範囲、各行のプレフィックスと内容の範囲、インライン要素の範囲を返す。本部品はそれらを変更せず、範囲の置換だけを行う。
  - yaml-front-matter は、フロントマターの検出、キーパスの照合、値の書き戻し用の整形を担う。本部品は整形結果を値の範囲にそのまま挿入し、区切りや引用符やインデントを自分で付けない。
  - 出力する PO エントリは po-format のエントリの表現であり、本部品はエントリの表現を再定義しない。msgid のエスケープは po-format が行う。
  - 参照コメントに書くファイル名は呼び出し側が渡す。行番号は 1 起点で、ファイルの先頭から数える。
  - 本部品は、エラーと警告を project-foundation の診断として呼び出し側に返し、自分で標準出力・標準エラー出力に書いたりプロセスを終了したりしない。

## Requirements

### Requirement 1: 翻訳対象の判定
**Objective:** As a 翻訳者, I want 文書の本文だけが翻訳単位になり、コードや URL が翻訳単位にならないこと, so that 訳すべき文だけに集中でき、書式を壊す心配がない

#### Acceptance Criteria
1. The 翻訳単位処理 shall 段落（リスト項目内・引用内の段落を含む）を、その内容を 1 つの翻訳セグメントとして扱う。
2. The 翻訳単位処理 shall ATX 見出しと setext 見出しを、見出しの内容（`#` と setext の下線を除く）を 1 つの翻訳セグメントとして扱う。
3. The 翻訳単位処理 shall 強調・リンク・画像・コードスパン・自動リンク・インライン HTML・バックスラッシュエスケープ・文字参照などのインライン記法を、原文の表記のまま翻訳セグメントの論理テキストに含める。
4. The 翻訳単位処理 shall 画像の alt を、それを含む段落または見出しの論理テキストの一部（`![alt](url)` の形）として翻訳対象にし、別の翻訳セグメントにはしない。
5. The 翻訳単位処理 shall コードブロック（フェンス・インデント）、HTML ブロック、リンク参照定義、区切り線を翻訳セグメントにせず、原文のまま保持する。
6. If 見出しまたは段落の論理テキストが空であるか空白だけである, then the 翻訳単位処理 shall それを翻訳セグメントにしない。
7. When 本文に方言固有の種類のブロック（CommonMark 以外の種類）が含まれる, the 翻訳単位処理 shall そのブロック自体を翻訳セグメントにせず、そのブロックが子として持つ段落や見出しは通常どおり翻訳セグメントとして扱う。
8. Where 呼び出し側がフロントマターのキーパスを 1 つ以上指定している, the 翻訳単位処理 shall キーパスに一致したスカラー値を翻訳セグメントとして扱う。
9. If 呼び出し側がフロントマターのキーパスを指定していない, then the 翻訳単位処理 shall フロントマターの範囲を検出して本文から切り離したうえで、その内容を YAML として解析せず、全体を原文のまま保持する。
10. If 指定したキーパスに一致する値がない, then the 翻訳単位処理 shall 診断を出さずにそのキーパスを無視する。
11. If 指定したキーパスに一致した値がスカラーでない（マッピングまたはマッピングを含む列）, then the 翻訳単位処理 shall 警告の診断を返し、その値を翻訳セグメントにしない。
12. If 指定したキーパスに一致したスカラー値が空であるか空白だけである, then the 翻訳単位処理 shall 診断を出さずにその値を翻訳セグメントにしない。

### Requirement 2: msgid の正規化
**Objective:** As a 翻訳者, I want msgid に行頭の記号が混ざらず、原文の改行がそのまま見えること, so that 訳すべき文が読みやすく、原文の折り返しの意図が分かる

#### Acceptance Criteria
1. When 翻訳セグメントが複数行にわたる, the 翻訳単位処理 shall 各行の行頭のプレフィックス（引用の `>`、リスト項目のインデントと 1 行目のマーカー、ブロック自身が取り除く先頭の空白）を除いた内容を、`\n` で連結して論理テキストにする。
2. The 翻訳単位処理 shall 原文の改行コードが LF でも CRLF でも、論理テキスト内の行の境界を `\n` にし、論理テキストに CR を含めない。
3. The 翻訳単位処理 shall 翻訳セグメントの最後の行の末尾の空白を論理テキストに含めず、その空白を翻訳対象外の原文として保持する。
4. The 翻訳単位処理 shall 最後の行以外の各行の末尾の空白（ハードブレークの 2 つ以上の空白を含む）を論理テキストに含める。
5. The 翻訳単位処理 shall 論理テキストを msgid とし、バックスラッシュエスケープや文字参照の解決、インライン記法の除去や置き換えを行わない。
6. When フロントマターのスカラー値が翻訳セグメントになる, the 翻訳単位処理 shall 引用符やブロックスカラーの記法を解決した論理的な値を msgid にする。
7. When フロントマターのスカラー値の論理的な値が改行で終わる, the 翻訳単位処理 shall 末尾の改行を msgid に含めず、再構成時に同じ数の改行を補って書き戻す。
8. The 翻訳単位処理 shall 空の msgid と改行で始まる msgid を生成しない。

### Requirement 3: 翻訳テンプレートのエントリの生成
**Objective:** As a monde-cli の開発者, I want 原文から PO エントリの列を受け取りたい, so that `monde extract` を薄い層として実装できる

#### Acceptance Criteria
1. When 呼び出し側が原文のバッファ、参照に書くファイル名、フロントマターのキーパスの一覧を渡す, the 翻訳単位処理 shall 翻訳セグメントごとのエントリの列を、ヘッダエントリを含まない形で返す。
2. The 翻訳単位処理 shall 同じ msgid を持つ翻訳セグメントを 1 つのエントリに統合し、フロントマターと本文の間でも統合する。
3. The 翻訳単位処理 shall エントリを、各 msgid が文書内で最初に出現する位置の順（フロントマター、本文の順）に並べる。
4. The 翻訳単位処理 shall 各エントリに、翻訳セグメントの出現ごとに 1 つの参照（ファイル名と、出現の先頭の 1 起点の行番号）を出現順に付ける。
5. The 翻訳単位処理 shall 各エントリに、要素の種類を示す抽出コメントを付ける。種類は `heading`（レベル付き）、`paragraph`、`list item`、`block quote`、`front matter`（キーパス付き）の英語の語彙で表し、リスト項目や引用の入れ子は外側から順に並べる。
6. When 同じ msgid が異なる種類の要素として出現する, the 翻訳単位処理 shall 種類ごとに 1 つずつ、重複のない抽出コメントを付ける。
7. The 翻訳単位処理 shall 各エントリの msgstr を空にし、fuzzy などのフラグを付けない。
8. The 翻訳単位処理 shall 各翻訳セグメントについて、文書内の出現位置（範囲と行番号）と要素の種類を呼び出し側から参照できるようにする。
9. The 翻訳単位処理 shall 生成するエントリの列を po-format で書き出したとき、`msgfmt --check` を通る内容にする。

### Requirement 4: 訳文の差し戻しによる再構成
**Objective:** As a 文書の保守者, I want 翻訳済み Markdown が原文の書式をバイト単位で保ったまま本文だけ訳されていること, so that 差分レビューとバージョン管理がしやすい

#### Acceptance Criteria
1. When 呼び出し側が原文のバッファ、翻訳カタログ、フロントマターのキーパスの一覧、fuzzy を採用するかの指定、原文の改行コードを渡す, the 翻訳単位処理 shall 翻訳対象の範囲だけを置き換えた出力バッファを返す。
2. The 翻訳単位処理 shall 翻訳セグメント以外のすべてのバイト（リスト記号、強調記号、空行、インデント、改行コード、コードブロック、HTML ブロック、フロントマターの区切りとキー、コメント）を原文のまま出力する。
3. When 翻訳セグメントに対応するエントリをカタログから探す, the 翻訳単位処理 shall msgctxt のないエントリのうち msgid が一致するものを使い、廃止エントリを無視する。
4. When 対応するエントリが翻訳済み（fuzzy でなく msgstr が空でない）である, the 翻訳単位処理 shall msgstr を訳文として差し戻す。
5. If 対応するエントリがない、または msgstr が空である, then the 翻訳単位処理 shall 原文をそのまま出力する。
6. While fuzzy を採用しない指定である, when 対応するエントリが fuzzy である, the 翻訳単位処理 shall 原文をそのまま出力する。
7. While fuzzy を採用する指定である, when 対応するエントリが fuzzy で msgstr が空でない, the 翻訳単位処理 shall msgstr を訳文として差し戻す。
8. When 訳文を複数行のブロックに差し戻す, the 翻訳単位処理 shall 訳文の各行に行頭のプレフィックスを付ける。原文に対応する行がある間はその行の元のプレフィックスをそのまま使い、訳文の行数が原文より多い場合は、引用の `>` とリスト項目の継続行のインデントを補ったプレフィックスを付ける。
9. When 訳文の行の境界を出力する, the 翻訳単位処理 shall 呼び出し側から渡された原文の改行コードを使う。
10. When フロントマターのスカラー値に訳文を差し戻す, the 翻訳単位処理 shall yaml-front-matter の整形結果を値の範囲にそのまま挿入し、区切り・引用符・インデントを自分で付け加えない。
11. If 訳文に空行が含まれる、または訳文のいずれかの行が行頭でブロックを開始し得る記号（`#`、`>`、リストマーカー、フェンス、区切り線など）で始まる、または 1 行の見出しの訳文に改行が含まれる, then the 翻訳単位処理 shall 警告の診断を返したうえで、訳文をそのまま出力する。
12. The 翻訳単位処理 shall 翻訳セグメントの判定と msgid の正規化を抽出時と再構成時で同一にし、抽出で生成した msgid を持つエントリが再構成時に必ず見つかるようにする。

### Requirement 5: ラウンドトリップの保証
**Objective:** As a 文書の保守者, I want 翻訳がない文書や原文と同じ訳が与えられた文書が、元のファイルとバイト単位で一致すること, so that 書式保持の正しさを機械的に検証でき、未翻訳の文書に差分が出ない

#### Acceptance Criteria
1. When 翻訳カタログが空、またはすべてのエントリが未翻訳である, the 翻訳単位処理 shall 原文とバイト単位で同一の出力を返す。
2. When すべての翻訳セグメントについて msgstr が msgid と同じ内容である, the 翻訳単位処理 shall 原文とバイト単位で同一の出力を返す。
3. The 翻訳単位処理 shall CommonMark spec 0.31.2 のすべてのテストケースの入力について、5.1 と 5.2 を満たす。
4. The 翻訳単位処理 shall 改行コードが CRLF の入力、LF と CRLF が混在する入力、末尾に改行のない入力についても、5.1 と 5.2 を満たす。

### Requirement 6: 翻訳率の集計に必要な情報
**Objective:** As a monde-cli の開発者, I want 再構成の結果と一緒に翻訳の状態の件数を受け取りたい, so that 翻訳率を計算して表示できる

#### Acceptance Criteria
1. When 再構成が完了する, the 翻訳単位処理 shall 文書内の翻訳セグメントの出現ごとに数えた件数を、翻訳済み・fuzzy・未翻訳（msgstr が空）・カタログにない、の 4 つの状態と合計で返す。
2. The 翻訳単位処理 shall 同じ msgid が複数回出現する場合、出現した回数だけ数える。
3. The 翻訳単位処理 shall fuzzy のエントリを、採用したかどうかにかかわらず fuzzy として数える。
4. The 翻訳単位処理 shall 翻訳セグメントにならなかった要素（コードブロック、空の見出し、無視したフロントマターのキーなど）を件数に含めない。

### Requirement 7: 入力の異常と診断
**Objective:** As a monde-cli の開発者, I want 入力の異常が診断として返り、部分的な出力が出ないこと, so that エラーメッセージの表示と終了コードを CLI 層で一貫して扱える

#### Acceptance Criteria
1. If 原文が正しい UTF-8 でない, then the 翻訳単位処理 shall 位置を示すエラーの診断を返し、出力を生成しない。
2. While フロントマターのキーパスが 1 つ以上指定されている, if フロントマターの YAML が解析できない（対応外の構文を含む場合を含む）, then the 翻訳単位処理 shall エラーの診断を返し、出力を生成しない。
3. If 指定したキーパスの書式が不正である, then the 翻訳単位処理 shall どのキーパスかを示すエラーの診断を返し、出力を生成しない。
4. If 訳文が正しい UTF-8 でない、または NUL を含む, then the 翻訳単位処理 shall どのエントリかを示すエラーの診断を返し、出力を生成しない。
5. If メモリの確保に失敗する, then the 翻訳単位処理 shall エラーの診断を返し、出力を生成しない。
6. The 翻訳単位処理 shall すべての診断を英語のメッセージで、呼び出し側から渡されたファイル名と 1 起点の行番号（位置が不明な場合は 0）を添えて返す。
7. The 翻訳単位処理 shall 警告の診断だけが発生した場合、出力を生成し、処理を成功として扱う。
8. If 翻訳セグメントの論理テキスト（msgid）が NUL を含む, then the 翻訳単位処理 shall どのセグメントかを示すエラーの診断を返し、出力を生成しない。
