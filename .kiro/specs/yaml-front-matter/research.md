# 調査と設計判断の記録: yaml-front-matter

## Summary
- **Feature**: `yaml-front-matter`
- **Discovery Scope**: Extension（既存のモジュール構成に、新しいモジュール `src/yaml/` を加える。既存のモジュールは変更しない）
- **Key Findings**:
  - 既存の 2 つのパーサ（po、markdown）が、本部品の型とエラーの扱いの手本になる。markdown は「内容を複製せず、オフセットだけを持つ構文木」「アリーナによる一括解放」「確保関数の差し替え」「再帰を使わない」という方式で、メモリ不足と深い入れ子の要件を満たしている。本部品も同じ方式を採る。
  - foundation は、本部品が必要とする型をすでに持つ。範囲は `mnd_span_t`、行番号は `mnd_source_line_of`（LF と CRLF を数え、単独の CR を数えない）、改行コードは `mnd_eol_detect`、UTF-8 の検証は `mnd_utf8_validate`、診断は `mnd_diag_list_t`。新しい型を foundation に加える必要はない。
  - YAML 1.2 のうち、フロントマターで実際に使われるのは、ブロック形式のマッピングとシーケンス、フロー形式の短いリスト、4 種類のスカラーのスタイル、コメントである。これらの字句の規則（プレーンスカラーに使えない先頭の文字、`: ` と ` #` による終端、ダブルクオートのエスケープ、ブロックスカラーのヘッダとチョンプ、行の折り返し）は仕様の範囲が明確で、手書きで実装できる。
  - 訳文をプレーンスカラーのまま書き戻すと、YAML の読み手（静的サイトジェネレータなど）が文字列以外の型に解釈する訳文がある（`true`、`123`、`null`、`~` など）。原文がプレーンでも、こうした訳文はダブルクオートに切り替える必要がある。

## Research Log

### 既存のモジュールの規約と方式
- **Context**: 本部品の公開 API の形と、メモリ・エラーの扱いを既存のモジュールに揃えるために確認した。
- **Sources Consulted**: `src/foundation/*.h`、`src/markdown/md.h`、`src/markdown/md_parse.h`、`src/po/po.h`、`.kiro/specs/markdown-parser/design.md`、`tests/markdown/test_alloc.h`、`cmake/MondeTargets.cmake`、`.kiro/steering/structure.md`
- **Findings**:
  - 構文木は内容を複製せず `mnd_span_t` で指す。文書は不透明な型で、アリーナにすべてのノードを持ち、`*_doc_free` で一括で解放する。
  - 解析の入口は `bool mnd_md_parse(data, len, options, &out, diags)`。オプションに `path`（診断に付ける）と確保関数（`alloc`/`free`/`ctx`）を持つ。メモリ不足は `false` と `out of memory` の診断。成功時は診断を増やさない。
  - 行番号は内容全体の先頭を 1 行目とする。`mnd_source_line_of` は LF の位置で改行を数える。
  - テストは `tests/<module>/` に 1 ファイル 1 スイートで置き、n 回目の確保を失敗させる確保関数で解放漏れを検査している。
  - 短縮名の予約: `buf`、`diag`、`severity`、`utf8`、`eol`、`span`、`slice`、`source`、`file`、`wide`、`args`、`po`、`merge`、`md`。
- **Implications**: 本部品の短縮名は `yaml`（モジュール名も `yaml`）。文書型 `mnd_yaml_doc_t`、解析 `mnd_yaml_parse`、確保関数 `mnd_yaml_allocator_t` を markdown と同じ形にする。範囲と行番号の基準は、フロントマターの内容ではなく文書全体の先頭とする（7.1）。

### YAML 1.2 のサブセットの字句の規則
- **Context**: 要件 2、3、5 の「論理値」「スタイル」「安全に表現できるか」を具体的な規則に落とすために、YAML 1.2.2 の仕様を確認した。
- **Sources Consulted**: YAML 1.2.2 仕様（第 6 章 Structural Productions、第 7 章 Flow Style Productions、第 8 章 Block Style Productions、第 10 章 Core Schema）
- **Findings**:
  - **指示文字**: `-`、`?`、`:`、`,`、`[`、`]`、`{`、`}`、`#`、`&`、`*`、`!`、`|`、`>`、`'`、`"`、`%`、`@`、`` ` ``。プレーンスカラーはこれらで始められない（`-`、`?`、`:` は、後ろが空白でなければ始められる）。`@` と `` ` `` は予約で、使うとエラー。
  - **プレーンスカラーの終端**: ブロック文脈では `: `（または `:` の後ろが行末）と ` #`。フロー文脈ではさらに `,`、`[`、`]`、`{`、`}`。前後の空白は含まない。
  - **コメント**: 行頭、または空白の直後の `#` から行末まで。
  - **ダブルクオートのエスケープ**: `\0 \a \b \t \n \v \f \r \e \  \" \/ \\ \N \_ \L \P \xXX \uXXXX \UXXXXXXXX`、および行末の `\` による改行の除去。これ以外の `\` はエラー。
  - **シングルクオート**: `''` だけがエスケープ。
  - **行の折り返し**（複数行のプレーン・引用符付き）: 行の境目は 1 つの空白になる。間の空行は 1 つずつ改行になる。各行の先頭と末尾の空白は除く（ダブルクオートでは、行末の `\` でその行の折り返しを抑止できる）。
  - **ブロックスカラー**: ヘッダは `|` または `>` に、チョンプ指示子（なし = clip: 末尾の改行を 1 つ残す、`-` = strip: 残さない、`+` = keep: すべて残す）とインデント指示子（1〜9）を任意の順で付け、その後ろはコメントだけ。内容のインデントは、指示子があれば親のインデント + 指示子、なければ最初の空でない行のインデント。リテラルは改行を保つ。折り返しでは、「より深くインデントされた行」と空白だけの行の前後は折り返さない。
  - **ブロックのコレクション**: マッピングの項目は同じインデントの `key: value`。シーケンスの項目は `- item`。マッピングの値としてのシーケンスは、キーと同じインデントでもよい（`key:\n- a`）。インデントにタブは使えない。
  - **Core Schema**: プレーンスカラーのうち `null | Null | NULL | ~ | （空）`、`true | True | TRUE | false | False | FALSE`、10 進・8 進（`0o`）・16 進（`0x`）の整数、小数と指数、`.inf | -.inf | .nan`（大文字小文字の変種を含む）は、文字列ではない型に解釈される。
- **Implications**: 解析の規則（本書 Components の Scalar と Block、Flow）と、整形の「安全さ」の規則（Formatter）を、上記のとおりに定める。Core Schema の非文字列の形は、整形の「プレーンのままにできない」条件に加える。

### キーパスと CLI の指定方法
- **Context**: 4.1〜4.8 のキーパスの書式を、monde-cli の `--front-matter-keys` と揃える。
- **Sources Consulted**: `.kiro/specs/cli-args/requirements.md`（カンマ区切りのリスト値）、`.kiro/specs/monde-cli/brief.md`、`docs/inputs/qa.md`（Q3-1）
- **Findings**: CLI は `--front-matter-keys title,description` のようにカンマで分けた文字列の列を渡す。cli-args はカンマを区切りとして扱うため、キーパスにカンマは使えない。ドットはカンマと衝突しない。
- **Implications**: キーパスの書式は「`.` で区切ったセグメントの列。セグメントは空でない。シーケンスは番号で指定せず、すべての要素を対象にする」とする。`.` を含むキーは指定できない（4.8）。本部品は 1 本のキーパスを受け取り、カンマの分割は CLI 側が行う。

## Architecture Pattern Evaluation

| Option | Description | Strengths | Risks / Limitations | Notes |
|--------|-------------|-----------|---------------------|-------|
| 行の表 + インデントのスタックによる解析 | 物理的な行の表を先に作り、ブロックの構造はインデントのスタックで、フロー形式とスカラーは文字単位の走査で解析する | インデントの規則と行番号の扱いが単純になる。ブロックスカラーの範囲を行単位で決めやすい。再帰を使わずに書ける | YAML 全体の文法を表現できない（必要ない） | **採用** |
| YAML 1.2 の文法に沿った再帰下降パーサ | 仕様の生成規則をそのまま関数にする | 仕様との対応が明確 | 再帰が深くなる（6.9 に反する）。サブセットには過剰 | 不採用 |
| 既存の C 実装（libyaml）を取り込む | ライブラリをソースごと取り込む | 正しさの実績 | 外部依存ゼロの方針に反する。原文上の範囲とスタイルを返さない | 不採用（自前で実装する） |

## Design Decisions

### Decision: 範囲と行番号の基準を文書全体の先頭にする
- **Context**: 7.1。translation-units は、フロントマターのスカラーと本文のブロックを同じ文書の範囲として置換し、参照コメントに文書全体の行番号を書く。
- **Alternatives Considered**:
  1. パーサにフロントマターの内容だけを渡し、オフセットを呼び出し側で足す
  2. パーサに文書全体と内容の範囲を渡し、文書全体を基準にしたオフセットと行番号を返す
- **Selected Approach**: 2。`mnd_yaml_parse(data, len, content, ...)` は文書全体 `data[0..len)` と、解析する範囲 `content` を受け取る。
- **Rationale**: markdown-parser が `body_start` で同じ方式を採っており、呼び出し側の計算を減らせる。
- **Trade-offs**: 単体テストでも範囲を渡す必要がある（`{0, len}` を渡せばよい）。

### Decision: 構文木をアリーナに置き、確保関数を差し替えられるようにする
- **Context**: 6.7（メモリ不足で解放漏れがない）、6.10（一括解放）、6.9（深い入れ子）。
- **Selected Approach**: markdown-parser と同じ。ノード、ノードの配列、論理値の文字列をすべて文書のアリーナに確保し、`mnd_yaml_doc_free` で一括で解放する。確保関数はオプションで差し替えられる（テストで n 回目の確保を失敗させる）。
- **Rationale**: 実績のある方式を再利用し、解放の手順が木の形に依存しない。
- **Trade-offs**: 確保関数の型を markdown と重複して定義する（モジュール間の横の依存を作らないため）。将来 foundation に移すなら両方を置き換える。

### Decision: 論理値を解析時に求めて文書に保持する
- **Context**: 3.5〜3.9。キーの照合（4.6）と msgid の生成が論理値を使う。
- **Alternatives Considered**:
  1. 範囲だけを持ち、論理値は必要なときに関数で求める（markdown の `mnd_md_logical_text` と同じ）
  2. 解析時に論理値を求め、文書のアリーナに持つ
- **Selected Approach**: 2。各スカラーのノードが `value`（NUL 終端の UTF-8）と `value_len` を持つ。
- **Rationale**: スカラーの数は少なく、キーの照合で何度も使う。エスケープの誤りを解析時に検出できる（6.5）。
- **Trade-offs**: メモリを内容の分だけ余分に使う（フロントマターは小さい）。

### Decision: 値のないキーを、`:` の直後の空の範囲を持つ空のプレーンスカラーにする
- **Context**: 2.8。`key:` のように値がないキーを翻訳対象にしても、書き戻せるようにする。
- **Selected Approach**: 空のプレーンスカラー（`value_len == 0`、`span.start == span.end`、`:` の直後）。整形器は、空の範囲に書き戻すときに先頭に 1 つの空白を付ける。
- **Rationale**: 範囲置換だけで `key: 訳文` を作れ、範囲の外側（キー、コメント）を変えない（5.8）。
- **Trade-offs**: 空の範囲が「`:` の直後」という位置の規約を整形器が知っている必要がある。

### Decision: 整形の「安全さ」の判定を保守的にし、迷ったらダブルクオートにする
- **Context**: 5.2〜5.5。YAML の読み手が訳文を別の意味に解釈することを防ぐ。
- **Selected Approach**: 元のスタイルを維持できる条件を明示的な表で定め、条件を満たさないときはダブルクオートに切り替える。プレーンでは、Core Schema で文字列以外に解釈される形（`true`、`123`、`null`、`~`、`.inf` など）も切り替えの条件に含める。ブロックスカラーで、チョンプ指示子で表せない末尾の改行は、要件のとおりダブルクオートに切り替える（チョンプ指示子を変える案は、要件 5.3 の「ヘッダを維持する」に反するため採らない）。
- **Rationale**: 切り替えの誤り（本当は安全だったのに引用符を付ける）は見た目の違いにとどまるが、判定の漏れは意味の変化を生む。
- **Trade-offs**: 原文が `title: Hello` で訳文が `2024` のような場合に `"2024"` になる。
- **Follow-up**: 整形後の内容を解析し直して論理値が訳文と一致することを、テストで網羅的に確かめる（8.2）。

### Decision: 整形は値のノードだけを対象にし、書き戻しの結果を知らせない
- **Context**: 簡素化。
- **Selected Approach**: `mnd_yaml_format_value` は、置き換えるバイト列だけを返す。スタイルが切り替わったかどうかは返さない。キーのノードに対する整形は未定義とせず、値と同じ規則で整形する（translation-units はキーを翻訳しない）。
- **Rationale**: 現在の要件に、切り替えの通知を必要とするものがない。
- **Trade-offs**: 将来、切り替えを警告として出したくなったら、結果の構造体を加える（Revalidation Trigger）。

## Risks & Mitigations
- YAML の折り返しとブロックスカラーの規則の誤読 — 仕様の例を単体テストに写し、論理値を確かめる。整形後の再解析による往復のテストで、解析と整形の食い違いを検出する。
- インデントの規則（マッピングの値としての同じインデントのシーケンス、ブロックスカラーの内容のインデントの自動検出）の取りこぼし — 代表的なフロントマター（Jekyll、Hugo、Astro の例）を模したテストデータで確かめる。
- 深い入れ子（フロー形式の括弧の入れ子、ブロックの入れ子）でのスタックあふれ — 再帰を使わず、明示的なスタックを使う。10,000 段の入力でテストする。
- 行番号の数え方の差（単独の CR） — foundation の規則に従い、CR だけの改行は改行と数えない。パーサは単独の CR を通常の文字として扱う（YAML では印字可能文字ではないためエラー）。
