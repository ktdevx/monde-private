# Requirements Document

## Project Description (Input)
**誰が困っているか**: Monde の開発者（とくに translation-units を実装する開発者）。Markdown 文書の YAML フロントマターには `title` や `description` など翻訳すべき値が含まれるが、外部の YAML ライブラリは使えない。指定したキーの値だけを抽出し、訳文に置き換えても周囲の YAML をバイト単位で保つ必要がある。

**現状**: YAML パーサはまだない。

**何を変えるか**:
- 文書先頭の `---` で囲まれたフロントマターを検出し、後ろの本文の開始位置を markdown-parser に受け渡せるようにする。
- フロントマターでよく使われる YAML のサブセットを手書きで解析し、キーパス（ネストしたキーを含む）ごとにスカラー値とそのソース範囲を返す再利用部品を用意する。
- 解析対象: マッピング、シーケンス（ブロック形式、可能ならフロー形式）、プレーン・シングルクオート・ダブルクオートのスカラー、ブロックスカラー（`|`、`>`）、コメント。
- スカラー値の論理値（アンエスケープ後の文字列）と、原文上の範囲・スタイル（引用符の種類、ブロックスカラーのインデントなど）を両方保持する。
- 訳文を書き戻すときに、元のスタイルのまま安全に表現できるかを判断して整形する部品を提供する（例: 引用符のエスケープ）。
- 非対応の構文（アンカー、エイリアス、タグ、複数ドキュメント）を検出して報告する。
- 範囲外: YAML 仕様の完全な対応、YAML 全体の再シリアライズ、TOML など YAML 以外のフロントマター、どのキーを翻訳するかの判断と CLI オプションの解釈（translation-units と monde-cli が担う）。

**制約**: project-foundation の上に構築する。非対応の構文を見つけたときにエラーにするかそのまま出力するか（Q3-2）を要件で確定する。キーパスの指定方法（例: ネストしたキーの区切り文字）を、monde-cli のオプション仕様と揃える。

## Introduction
yaml-front-matter は、Markdown 文書の先頭にある YAML フロントマターを検出し、フロントマターでよく使われる YAML のサブセットを解析する汎用の部品である。利用者は Monde の開発者で、とくに translation-units を実装する開発者である。translation-units はこの部品を使って、指定したキーの値（スカラー）を論理的な文字列として取り出し、訳文をその値の原文上の範囲に書き戻す。そのため、各スカラーについて、アンエスケープや折り返しを解決した論理値と、原文上のバイト範囲・行番号・スタイル（引用符の種類、ブロックスカラーのインデントなど）を両方返すこと、訳文を YAML として安全な表現に整形できることが求められる。本部品は Monde 固有の知識（どのキーを翻訳するか、CLI オプションの解釈）を持たず、単体テストで挙動を検証できる。

### 要件確認で決めた挙動
- アンカー、エイリアス、タグ、ディレクティブなどの非対応の構文を見つけた場合は、エラーにする（Q3-2）。行番号付きのエラーの診断を返し、解析結果を返さない。
- キーパスは、ネストしたマッピングのキーを `.` で区切って表す（例: `seo.title`）。パスの途中または末尾がシーケンスに当たった場合は、そのシーケンスのすべての要素を対象にする（例: `tags` ですべてのタグ、`authors.name` ですべての著者の `name`）。要素の番号による指定は行わない。
- 訳文を元のスタイルのままでは安全に表現できない場合は、その値をダブルクオートのスカラーに切り替えて、必要なエスケープを施して書き戻す。
- フロントマターは、文書の 1 行目が `---` の場合に始まり、それ以降で最初に現れる `---` または `...` の行で終わる。閉じる行がない場合は、フロントマターがないものとして扱い、文書全体を本文とする。

## Boundary Context
- **In scope**:
  - 文書先頭のフロントマターの検出と、フロントマターの内容の範囲・本文の開始位置の報告
  - YAML サブセットの解析: ブロック形式とフロー形式のマッピング・シーケンス、プレーン・シングルクオート・ダブルクオートのスカラー、ブロックスカラー（`|`、`>`、チョンプ指示子、インデント指示子）、コメント、空行
  - 各スカラーの論理値と、原文上のソース範囲・行番号・スタイル
  - キーパスによるスカラーの参照
  - 訳文を書き戻すための値の整形（スタイルの維持と、必要な場合のダブルクオートへの切り替え）
  - 非対応の構文の検出と、エラーとしての報告
- **Out of scope**:
  - YAML 1.2 仕様の完全な対応（アンカー、エイリアス、タグ、ディレクティブ、複雑なキー `?`、複数ドキュメントなど）
  - YAML 全体の再シリアライズ、値の型（数値、真偽値、null）の解釈
  - TOML（`+++`）など YAML 以外の形式のフロントマター
  - どのキーを翻訳対象にするかの判断、msgid の組み立て、範囲置換による出力の再構成（translation-units が担う）
  - `--front-matter-keys` などの CLI オプションの解釈（monde-cli と cli-args が担う）
  - ファイルの読み書き、BOM の除去、メッセージの表示、終了コードの決定（foundation と monde-cli が担う）
- **Adjacent expectations**:
  - 呼び出し側は、BOM を除去した後の文書の内容を本部品に渡す。
  - markdown-parser は、本部品が返した本文の開始位置から Markdown を解析する。
  - translation-units は、本部品が返すソース範囲と整形した訳文を使って範囲置換を行う。本部品は原文の内容を変更しない。
  - monde-cli は、利用者が指定したキーパス（例: `--front-matter-keys title,seo.title`）を、本部品のキーパスの書式のまま translation-units に渡す。
  - 本部品は、ソース範囲を project-foundation のソース範囲の型で表し、エラーを project-foundation の診断として返す。自分で標準出力・標準エラー出力に書いたり、プロセスを終了したりしない。

## Requirements

### Requirement 1: フロントマターの検出
**Objective:** As a translation-units の開発者, I want 文書の先頭にフロントマターがあるかどうかと、その範囲を知りたい, so that フロントマターと本文を切り分けて、それぞれを適切な部品で解析できる

#### Acceptance Criteria
1. When 文書の 1 行目が `---`（後ろに空白・タブだけが続いてもよい）であり、それ以降に `---` または `...`（後ろに空白・タブだけが続いてもよい）だけからなる行がある, the フロントマター検出器 shall 1 行目から最初に現れたその行までをフロントマターとして検出する。
2. When フロントマターを検出した, the フロントマター検出器 shall フロントマター全体の範囲（開きの行から閉じの行の行末記号まで）、開きと閉じの行に挟まれた内容の範囲、本文の開始位置（閉じの行の行末記号の直後）を、渡された内容の先頭を基準とするバイトオフセットと行番号で返す。
3. When 文書の 1 行目が `---` の行でない, the フロントマター検出器 shall フロントマターがないことを示し、本文の開始位置として 0 を返す。
4. If 1 行目が `---` の行であるが、閉じの行が見つからない, then the フロントマター検出器 shall フロントマターがないことを示し、本文の開始位置として 0 を返す。
5. When 開きと閉じの行の間に内容がない, the フロントマター検出器 shall 内容が空のフロントマターとして検出する。
6. When 閉じの行が文書の最後の行で、行末記号を持たない, the フロントマター検出器 shall 文書の長さを本文の開始位置として返す。
7. The フロントマター検出器 shall 行末記号として LF と CRLF を受け付け、検出の前後で渡された内容のバイト列を変更しない。

### Requirement 2: YAML サブセットの解析
**Objective:** As a translation-units の開発者, I want フロントマターでよく使われる YAML を構造として知りたい, so that ネストしたキーやリストの値も翻訳対象にできる

#### Acceptance Criteria
1. When 呼び出し側がフロントマターの内容の範囲を渡して解析を要求する, the YAML パーサ shall 内容を 1 つのドキュメントとして解析し、マッピング・シーケンス・スカラーからなる木を返す。
2. The YAML パーサ shall インデントによるブロック形式のマッピング（`key: value`）とシーケンス（`- item`）を、任意の深さの入れ子で解析する。
3. The YAML パーサ shall フロー形式のシーケンス（`[a, b]`）とマッピング（`{k: v}`）を、ブロック形式の値として、また互いの入れ子として解析する。
4. The YAML パーサ shall マッピングのキーとして、プレーン・シングルクオート・ダブルクオートのスカラーを受け付ける。
5. The YAML パーサ shall コメント（行頭、または空白の直後の `#` から行末まで）と空行を、値の一部とせずに読み飛ばし、プレーンスカラーの途中にある `#`・`&`・`*`・`!` などは値の一部として扱う。
6. The YAML パーサ shall マッピングのキーとシーケンスの要素を、原文の出現順に返す。
7. When 内容が空、または空行とコメントだけからなる, the YAML パーサ shall 値を持たない空のドキュメントを返す。
8. When マッピングのキーに値が書かれていない（`key:` の後ろが空）, the YAML パーサ shall その値を空のプレーンスカラーとして返し、その位置（キーの `:` の直後）を返す。
9. The YAML パーサ shall スカラーの値の型（数値、真偽値、null など）を解釈せず、すべてのスカラーを文字列として返す。
10. The YAML パーサ shall 解析の前後で、渡された内容のバイト列を変更しない。

### Requirement 3: スカラーの論理値とソース範囲
**Objective:** As a translation-units の開発者, I want 各スカラーの論理的な文字列と原文上の範囲・スタイルを知りたい, so that 論理値を msgid にし、訳文を原文の正しい範囲に書き戻せる

#### Acceptance Criteria
1. The YAML パーサ shall すべてのキーと値のスカラーに、渡された内容を基準とするソース範囲（開始を含み終了を含まないバイトオフセット）と、開始行と終了行の行番号を持たせる。
2. The YAML パーサ shall スカラーのソース範囲を、引用符付きのスカラーでは開きと閉じの引用符を含む範囲とし、ブロックスカラーではヘッダ（`|` または `>` と指示子）から最後の内容の行の終わりまでとし、後ろのコメントと行末記号を含めない。
3. The YAML パーサ shall スカラーのスタイル（プレーン、シングルクオート、ダブルクオート、リテラルブロック `|`、折り返しブロック `>`）を返す。
4. The YAML パーサ shall ブロックスカラーについて、チョンプ指示子（なし、`-`、`+`）、インデント指示子の有無と値、内容の行のインデント幅を返す。
5. The YAML パーサ shall ダブルクオートのスカラーの論理値として、YAML 1.2 が定めるエスケープシーケンス（`\n`、`\t`、`\"`、`\\`、`\uXXXX` など）を解決した文字列を返す。
6. The YAML パーサ shall シングルクオートのスカラーの論理値として、`''` を `'` に置き換えた文字列を返す。
7. When プレーンまたは引用符付きのスカラーが複数行にまたがる, the YAML パーサ shall YAML 1.2 の行の折り返しの規則（改行を 1 つの空白に置き換え、空行を改行として残し、行頭と行末の空白を除く）を適用した論理値を返す。
8. The YAML パーサ shall ブロックスカラーの論理値として、内容の行のインデントを除き、リテラルでは改行をそのまま残し、折り返しでは YAML 1.2 の折り返しの規則を適用し、チョンプ指示子に従って末尾の改行を処理した文字列を返す。
9. The YAML パーサ shall 論理値の改行を、原文の行末記号（LF または CRLF）にかかわらず LF で表す。

### Requirement 4: キーパスによる参照
**Objective:** As a translation-units の開発者, I want 利用者が指定したキーパスに当たるスカラーを取り出したい, so that 指定されたキーの値だけを翻訳対象にできる

#### Acceptance Criteria
1. When 呼び出し側がキーパスを指定してスカラーを要求する, the YAML パーサ shall キーパスを `.` で区切った各セグメントを、ルートのマッピングから順にキーの論理値と照合する。
2. When キーパスの照合の途中または末尾でシーケンスに当たる, the YAML パーサ shall そのシーケンスのすべての要素に対して、残りのセグメントの照合を続ける。
3. When キーパスに当たる値がスカラー、またはスカラーを要素に持つシーケンスである, the YAML パーサ shall 当たったすべてのスカラーを、原文の出現順に、論理値・ソース範囲・行番号・スタイルとともに返す。
4. When キーパスに当たるキーがない, the YAML パーサ shall 該当がないことを示し、エラーとしない。
5. When キーパスに当たる値がマッピングである, the YAML パーサ shall その値をスカラーとして返さず、該当がスカラーでないことを呼び出し側が区別できるように示す。
6. The YAML パーサ shall キーの照合を、キーの原文の書き方（プレーン、引用符付き）にかかわらず、論理値の完全一致（大文字と小文字を区別する）で行う。
7. If キーパスが空、または空のセグメントを含む（例: `a..b`、`.a`）, then the YAML パーサ shall 照合を行わずに、不正なキーパスであることをエラーの診断として返す。
8. The YAML パーサ shall `.` を含むキーは、キーパスでは指定できないものとして扱う。

### Requirement 5: 訳文の書き戻しのための整形
**Objective:** As a translation-units の開発者, I want 訳文を元のスカラーの範囲に置き換えられる YAML の表現に整形したい, so that 訳文に記号や改行が含まれていてもフロントマターの構造を壊さず、周囲の YAML をバイト単位で保てる

#### Acceptance Criteria
1. When 呼び出し側がスカラーと訳文（論理値）を渡して整形を要求する, the 値の整形器 shall そのスカラーのソース範囲を置き換えるバイト列を返し、そのバイト列を同じ位置で解析し直すと論理値が訳文と一致するようにする。
2. When 訳文を元のスタイルのまま表現できる, the 値の整形器 shall 元のスタイルを維持して整形する（ダブルクオートでは `\` と `"` と制御文字をエスケープし、シングルクオートでは `'` を `''` にする）。
3. When 元のスタイルがブロックスカラーである, the 値の整形器 shall ヘッダ（スタイル、チョンプ指示子、インデント指示子）と内容の行のインデント幅を維持し、訳文の各行をそのインデントで出力する。
4. If 訳文を元のスタイルのままでは表現できない（例: プレーンスカラーの訳文が改行・`: `・` #` を含む、先頭が YAML の指示文字や空白である、末尾が空白である、ブロックスカラーの訳文がチョンプ指示子で表せない末尾の改行を持つ）, then the 値の整形器 shall その値をダブルクオートのスカラーに切り替え、必要なエスケープを施して整形する。
5. Where スカラーがフロー形式のコレクションの中にある, the 値の整形器 shall プレーンスカラーの訳文に `,`、`[`、`]`、`{`、`}` が含まれる場合も、ダブルクオートのスカラーに切り替える。
6. The 値の整形器 shall 複数行の出力の行末記号として、フロントマターで使われている行末記号（LF または CRLF）を使う。
7. The 値の整形器 shall 訳文の非 ASCII 文字を、エスケープせずに UTF-8 のまま出力する。
8. The 値の整形器 shall 整形の結果として、スカラーのソース範囲の外側のバイト列（キー、インデント、後ろのコメント、行末記号）を変更する内容を返さない。

### Requirement 6: 非対応の構文と不正な入力
**Objective:** As a monde-cli の開発者, I want 解析できないフロントマターについて理由と位置を受け取りたい, so that 意味を取り違えた翻訳を出力せずに、ユーザーに英語のエラーメッセージを表示できる

#### Acceptance Criteria
1. If 内容に、ノードの先頭に置かれたアンカー（`&name`）、エイリアス（`*name`）、タグ（`!` で始まる指示）、または行頭のディレクティブ（`%` で始まる行）、複雑なキー（`? `）が含まれる, then the YAML パーサ shall 解析結果を返さずに、非対応の構文の種類とその位置の行番号を持つエラーの診断を返す。
2. If 内容がインデントの不整合、閉じていない引用符やフロー形式の括弧、`key: value` として解釈できない行など、YAML のサブセットとして解析できない, then the YAML パーサ shall 解析結果を返さずに、その位置の行番号を持つエラーの診断を返す。
3. If インデントにタブが使われている, then the YAML パーサ shall 解析結果を返さずに、その位置の行番号を持つエラーの診断を返す。
4. If 同じマッピングに論理値が同じキーが複数ある, then the YAML パーサ shall 解析結果を返さずに、後から現れたキーの行番号を持つエラーの診断を返す。
5. If ダブルクオートのスカラーに YAML 1.2 が定めない、または不正なエスケープシーケンスが含まれる, then the YAML パーサ shall 解析結果を返さずに、その位置の行番号を持つエラーの診断を返す。
6. If 内容に不正な UTF-8 のバイト列が含まれる, then the フロントマター検出器と YAML パーサ shall 結果を返さずに、その位置の行番号を持つエラーの診断を返す。
7. If 処理中に必要なメモリを確保できない, then the フロントマター検出器、YAML パーサ、値の整形器 shall 異常終了せずに、結果を返さずにエラーの診断を返し、それまでに確保したメモリを解放する。
8. The フロントマター検出器、YAML パーサ、値の整形器 shall 診断のメッセージを英語で記録し、標準出力・標準エラー出力への書き込みやプロセスの終了を行わない。
9. The YAML パーサ shall 入れ子の深いマッピング・シーケンスやフロー形式の括弧を含む入力でも、異常終了せずに解析を完了するか、エラーの診断を返す。
10. When 呼び出し側が解析結果を解放する, the YAML パーサ shall 解析結果のために確保したメモリをすべて解放する。

### Requirement 7: 行番号と行末記号
**Objective:** As a translation-units の開発者, I want フロントマターのスカラーの行番号を文書全体の行番号で知りたい, so that 参照コメント（`#: file.md:行番号`）に正しい行番号を出せる

#### Acceptance Criteria
1. The フロントマター検出器と YAML パーサ shall 行番号を、渡された文書の内容全体の先頭を 1 行目とし、project-foundation のソース範囲の規則に従って数える。
2. The YAML パーサ shall LF と CRLF のどちらの行末記号を使う内容も同じ構造として解析し、行末記号をスカラーの内容の範囲に含めない。

### Requirement 8: 単体テストによる検証
**Objective:** As a Monde の開発者, I want 本部品の挙動を単体テストで確認したい, so that translation-units と切り離して YAML の扱いの正しさを保証できる

#### Acceptance Criteria
1. The yaml-front-matter のテスト shall フロントマターの検出、各スタイルのスカラーの論理値とソース範囲、キーパスによる参照、非対応の構文と不正な入力のエラーを、個別のテストで確認する。
2. The yaml-front-matter のテスト shall 各スタイルのスカラーについて、さまざまな訳文（記号、改行、引用符、非 ASCII を含むもの）を整形し、整形後の内容を解析し直した論理値が訳文と一致し、置き換えた範囲の外側のバイト列が原文と一致することを確認する。
3. The yaml-front-matter のテスト shall 整形せずに元のバイト列を書き戻した場合に、フロントマター全体が原文とバイト単位で一致することを確認する。
