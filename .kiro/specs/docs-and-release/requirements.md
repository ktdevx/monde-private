# Requirements Document

## Project Description (Input)
**誰が困っているか**: `monde` の利用者。`monde` を入手し、翻訳フローでの使い方を日本語で理解する必要がある。RFP は、日本語のドキュメントと、GitHub での配布を成果物として求めている。

**現状**: README.md は最小限の内容しかない。利用マニュアルとリリースのワークフローはない。

**何を変えるか**:
- 日本語の README と利用マニュアル（`docs/` 配下）で、インストール、ソースからのビルド、各サブコマンドとオプション、2 つの翻訳フローの手順がわかるようにする。README には概要、インストール、クイックスタート、ビルド手順、ライセンス、spec.txt などのサードパーティ表記を載せる。
- タグを付けると、GitHub Actions のワークフローが Windows、macOS、Linux 向けにビルドしてアーカイブを作り、GitHub Releases に公開する。バージョン番号の付け方を定める。

**範囲外**: パッケージマネージャーへの登録、英語版のドキュメント、機能の追加や変更、開発者向けの内部設計ドキュメント。

**制約**:
- ドキュメントは日本語で書く。利用マニュアルは monde-cli で確定したサブコマンドとオプションの仕様から作る。
- CC-BY-SA 4.0 のテストデータ（spec.txt）はリリース成果物に含めない。
- 著作権者は The Monde Authors、ライセンスは MIT とする。
- 利用マニュアルの既知の制限に、yaml-front-matter の design.md の「改訂」の節の「受け入れた制限」（ルートがインデント 0 のスカラーの継続、フロー形式の継続行のインデント、ダブルクオートの中の U+2028・U+2029）を載せる。
- 上流: monde-cli（CLI 仕様）、project-foundation（ビルドと CI）。

## Introduction
docs-and-release は、Monde の初版を利用者に届けるための 2 つの成果物を扱う。1 つは日本語のドキュメント（README と `docs/` 配下の利用マニュアル）で、利用者が `monde` を入手し、新規翻訳と原文更新の 2 つのフローを実行し、各サブコマンドとオプションの意味と既知の制限を確かめられるようにする。もう 1 つはリリースの自動化で、バージョンのタグを付けると Windows、macOS、Linux 向けのビルド済みバイナリのアーカイブが GitHub Releases に公開されるようにし、あわせてバージョン番号の付け方を定める。機能の追加や変更は行わず、monde-cli で確定した CLI の仕様をそのまま記述する。

### 要件確認で決めた事項
- バージョン番号は SemVer（`X.Y.Z`）とし、Git のタグは `v` 接頭辞付き（`vX.Y.Z`）とする。初版は `v0.1.0`。
- リリースでビルドする対象は Windows x64、macOS arm64、macOS x64、Linux x64 の 4 つ。
- アーカイブは Windows が zip、macOS と Linux が tar.gz。同梱物は実行ファイル、LICENSE、README。各アーカイブの SHA-256 をまとめたチェックサムのファイルも Release に添付する。
- 利用マニュアルは `docs/` 配下に章ごとの複数ファイルで置く。

## Boundary Context
- **In scope**:
  - README.md の全面的な更新（概要、インストール、クイックスタート、ソースからのビルド手順、ドキュメントへの案内、ライセンスとサードパーティの表記）
  - `docs/` 配下の利用マニュアル（インストール、2 つの翻訳フロー、サブコマンドとオプションのリファレンス、既知の制限）
  - バージョン番号の付け方と、タグとビルドに埋め込むバージョンの整合
  - タグを契機にしたリリースワークフロー（各 OS 向けのビルド、アーカイブの作成、チェックサムの生成、GitHub Releases への公開）
  - リリース成果物に含めるもの・含めないものの規定
- **Out of scope**:
  - パッケージマネージャー（Homebrew、winget、apt など）への登録
  - 英語版のドキュメント
  - 機能の追加や変更、CLI の仕様の変更（仕様は monde-cli で確定済み）
  - 開発者向けの内部設計ドキュメント（各 spec の design.md が担う）と、`docs/dev/`・`docs/inputs/` の内容の見直し
  - 継続的インテグレーション（push と pull request で動くビルドとテスト。project-foundation が担う）
  - リリースノートの本文の自動生成（Release の本文は人が書く。ワークフローは成果物の添付までを担う）
- **Adjacent expectations**:
  - monde-cli は、4 つのサブコマンドの位置引数、オプション、統計の表示、診断の形式、終了コードを確定した仕様として提供する。本 spec はそれを記述し、変更しない。
  - project-foundation は、3 行の共通のビルド手順（構成・ビルド・テスト）と、`BUILD_TESTING=OFF` でテスト用の依存を取得しないビルドを提供する。リリースワークフローはこの手順を使う。
  - monde-cli は、ビルド構成の 1 か所で決めたバージョン文字列を `--version` で表示する。本 spec はその値とタグの整合を求める。
  - yaml-front-matter の design.md の「改訂」の節の「受け入れた制限」は、利用マニュアルの既知の制限の出典とする。

## Requirements

### Requirement 1: README
**Objective:** As a `monde` を初めて知った利用者, I want リポジトリの README を読むだけで何ができるツールか、どう入手し、最初の 1 回をどう動かすかを知りたい, so that マニュアルを読み込む前に自分の用途に合うか判断して試せる

#### Acceptance Criteria
1. The README shall 日本語で、Monde が何をするツールか（Markdown を `.pot` / `.po` を介して翻訳するフローの支援、原文の書式をバイト単位で保持すること、翻訳作業そのものは PO 対応のツールに任せること）を冒頭で説明する。
2. The README shall 4 つのサブコマンド（`extract`、`init`、`update`、`translate`）と、それぞれの入力と出力を一覧で示す。
3. The README shall インストール方法として、GitHub Releases からの入手（対応する OS とアーキテクチャ、アーカイブの展開、実行ファイルの配置）と、ソースからのビルド（必要なツールとそのバージョン、共通の 3 行のビルド手順、`BUILD_TESTING=OFF` でテスト用の依存を取得せずに製品だけをビルドする方法）の両方を説明する。
4. The README shall クイックスタートとして、新規翻訳のフロー（`extract` → `init` → 翻訳 → `translate`）を、実際に実行できるコマンド列と各段階の入出力ファイルとともに示す。
5. The README shall 利用マニュアルの各章へのリンクを示し、詳しい説明をマニュアルに委ねる。
6. The README shall ライセンスが MIT License、著作権者が The Monde Authors であることを示す。
7. The README shall Monde の製品に含まれないサードパーティの資料（CommonMark spec の `spec.txt` は CC-BY-SA 4.0 でテスト専用、テストフレームワークの Naos はテスト専用）について、名称、用途、ライセンス、製品の実行ファイルと配布物に含まれないことを示す。
8. The README shall 初版の対応範囲（CommonMark 0.31.2 と YAML フロントマター）と、GFM など次の版で対応する予定のものを区別して示す。

### Requirement 2: 利用マニュアルの構成
**Objective:** As a 翻訳者または文書の保守者, I want 目的に応じて読む章がすぐに見つかるマニュアルがほしい, so that インストール、フローの手順、コマンドの詳細、制限をそれぞれ必要なときに参照できる

#### Acceptance Criteria
1. The 利用マニュアル shall `docs/` 配下に、少なくとも「インストール」「翻訳フロー」「コマンドリファレンス」「既知の制限」の 4 つの章をそれぞれ別のファイルとして持つ。
2. The 利用マニュアル shall 章の一覧と各章への相対リンクを持つ目次のファイルを `docs/` 配下に持ち、README から目次と各章に辿れる。
3. The 利用マニュアル shall すべての本文を日本語で書き、コマンド名、オプション名、ファイル名、CLI が出力するメッセージの例は英語の原文のまま示す。
4. The 利用マニュアル shall 各章の間の相互参照をリポジトリ内の相対リンクで書き、リポジトリをクローンした状態でも GitHub 上でもリンクが切れない。
5. The 利用マニュアル shall `docs/dev/` と `docs/inputs/` の内容を利用者向けの章として参照せず、利用者向けの章とそれらを混同させない。

### Requirement 3: インストールと翻訳フローの手順
**Objective:** As a 翻訳者, I want 入手から 2 つの翻訳フローの完了までを手順どおりに辿りたい, so that 初めてでも新規翻訳と原文更新の両方を間違いなく実行できる

#### Acceptance Criteria
1. The 利用マニュアル shall インストールの章で、GitHub Releases の各アーカイブと対応する OS・アーキテクチャの対応、アーカイブの展開と実行ファイルの配置、`monde --version` による動作確認の手順を示す。
2. The 利用マニュアル shall インストールの章で、ソースからのビルドに必要なツール（CMake の最低バージョン、各 OS で使えるコンパイラ）と、製品だけをビルドする手順、テストも含めてビルドして実行する手順を示す。
3. The 利用マニュアル shall 翻訳フローの章で、新規翻訳のフロー（`extract` → `init` → 翻訳者による `.po` の編集 → `translate`）を、各段階のコマンド、入出力ファイル、確認すべき表示（統計）とともに順に示す。
4. The 利用マニュアル shall 翻訳フローの章で、原文更新のフロー（更新後の原文で `extract` → `update` で既存の `.po` とマージ → fuzzy と未翻訳の差分を翻訳 → `translate`）を、各段階のコマンド、入出力ファイル、確認すべき表示とともに順に示す。
5. The 利用マニュアル shall 翻訳フローの章で、`update` の出力先に既存の `.po` と同じパスを指定して上書きできること、失敗時に既存の `.po` が変更されないことを示す。
6. The 利用マニュアル shall 翻訳フローの章で、未翻訳と fuzzy のエントリが既定では原文のまま出力されること、`--use-fuzzy` で fuzzy の訳を採用できること、翻訳率に fuzzy が含まれないことを示す。
7. The 利用マニュアル shall 翻訳フローの章で、YAML フロントマターの値を翻訳対象に含めるときに `extract` と `translate` の両方に同じ `--front-matter-keys` を指定する必要があることと、キーパスの書き方を示す。
8. The 利用マニュアル shall 翻訳フローの章で、`.po` の編集に Monde 自身は関与せず、PO 対応の翻訳プラットフォームやエディタで編集することを示す。
9. The 利用マニュアル shall 翻訳フローの章で、翻訳済み Markdown をバージョン管理で差分レビューする使い方を、原文の書式がバイト単位で保持されることとともに示す。

### Requirement 4: コマンドリファレンス
**Objective:** As a 翻訳者, I want 各サブコマンドの引数、オプション、表示、終了コードを正確に知りたい, so that 手作業でもスクリプトからでも意図どおりに `monde` を使える

#### Acceptance Criteria
1. The 利用マニュアル shall コマンドリファレンスの章で、`monde` 全体の使い方（サブコマンドの一覧、`--help` / `-h` / `help`、`--version`、引数なしの実行の結果）を示す。
2. The 利用マニュアル shall 4 つのサブコマンドそれぞれについて、位置引数（個数と順序）、すべてのオプション（短い形と長い形、値の形式、省略時の既定値）、入出力の既定（`-o/--output` の省略時は標準出力、`-` による標準入出力の指定）を、monde-cli の確定した仕様と一致する内容で示す。
3. The 利用マニュアル shall コマンドリファレンスに載せるオプションの一覧を、ビルドした `monde <subcommand> --help` の出力と過不足なく一致させる。
4. The 利用マニュアル shall `init` の言語コードの決め方（`-l/--language`、省略時の環境変数 `LC_ALL` → `LC_MESSAGES` → `LANG` の参照、`C` / `POSIX` の扱い、決められないときの使い方のエラー）を示す。
5. The 利用マニュアル shall `extract` の POT ヘッダに関するオプション（`--project-id-version`、`--msgid-bugs-address`）と省略時の値を示す。
6. The 利用マニュアル shall 各サブコマンドが成功時に標準エラー出力に表示する統計の内容と書式、`-q/--quiet` で抑止される表示とされない表示を示す。
7. The 利用マニュアル shall 診断の表示形式（`<path>:<line>: error: <message>` など）と、終了コード 0・1・2 のそれぞれの意味を示す。
8. The 利用マニュアル shall 文字コードと改行コードの扱い（UTF-8 のみ、BOM の読み込みと `translate` での引き継ぎ、`.pot` / `.po` は BOM なし、改行コードは主となる入力に合わせること）を示す。
9. The 利用マニュアル shall 翻訳対象の判定の規則（ブロック単位の翻訳単位、インライン記法は msgid に含める、コードブロック・HTML ブロック・リンク先 URL は対象外、画像の alt は対象、同一文は 1 つの msgid にまとめる）を利用者の視点で示す。
10. The 利用マニュアル shall 出力先のファイルが存在するときに確認なしで置き換えること、エラー時には出力先を作成も変更もしないことを示す。

### Requirement 5: 既知の制限
**Objective:** As a 文書の保守者, I want 対応していない記法や挙動を事前に知りたい, so that 想定外の結果を不具合と誤解せず、原文の書き方で回避できる

#### Acceptance Criteria
1. The 利用マニュアル shall 既知の制限の章で、初版で対応しない Markdown の記法（GFM の表、タスクリスト、取り消し線、自動リンク、脚注）と、それらがどう扱われるか（CommonMark としての解釈のまま翻訳単位になること）を示す。
2. The 利用マニュアル shall 既知の制限の章で、YAML フロントマターの対応範囲（対応しないもの: アンカー、エイリアス、タグ、複数ドキュメント）を示す。
3. The 利用マニュアル shall 既知の制限の章に、yaml-front-matter の設計で受け入れた制限を載せる: ルートがインデント 0 のプレーンスカラーは次の行へ継続できず、ルートでインデント 0 の内容を持つブロックスカラーも扱えない（エラーになる）こと。
4. The 利用マニュアル shall 既知の制限の章に、フロー形式の継続行のインデントを検査しない（厳密な YAML より受け付ける範囲が広いが、往復は壊れない）ことを載せる。
5. The 利用マニュアル shall 既知の制限の章に、ダブルクオートのキーの中の U+2028・U+2029 は UTF-8 のまま出力され、YAML 1.1 のパーサが読めないことがある（Monde はキーを翻訳しないため、値には影響しない）ことを載せる。
6. The 利用マニュアル shall 既知の制限の章で、1 回の実行で扱えるのは 1 ファイルであること、設定ファイルがないこと、複数形エントリは読み込めるだけで本格対応しないこと、翻訳率による出力の制御をしないことを示す。
7. The 利用マニュアル shall 既知の制限の章で、訳文が構造を変え得る内容（空行やブロックを開始し得る記号を含むなど）のときに警告が出ること、その場合の対処（訳文の見直し）を示す。

### Requirement 6: バージョン番号の付け方
**Objective:** As a Monde の保守者, I want バージョン番号の規則とタグの形式を定めたい, so that 利用者が互換性の変化を番号から読み取れ、タグ付けだけで正しいバージョンのリリースができる

#### Acceptance Criteria
1. The プロジェクト shall バージョン番号を `X.Y.Z` の 3 つの数の組（セマンティックバージョニング）とし、CLI の互換性を壊す変更で X を、互換性を保つ機能追加で Y を、修正のみで Z を上げる規則を README または利用マニュアルに示す。
2. The プロジェクト shall リリースのタグを `vX.Y.Z` の形式（`v` 接頭辞 + バージョン番号）とし、初版のタグを `v0.1.0` とする。
3. The プロジェクト shall `monde --version` が表示するバージョン文字列を、ビルド構成の 1 か所に書いたバージョン番号から決め、リリースのタグからその `v` 接頭辞を除いたものと一致させる。
4. The プロジェクト shall バージョン番号を上げる手順（ビルド構成のバージョンを書き換え、コミットし、同じ番号のタグを付けて push する）を、保守者向けの短い手順として README または `docs/` 配下に示す。
5. While X が 0 である, the プロジェクト shall CLI の互換性を壊す変更でも Y を上げることを許容し、その旨を規則に明記する。

### Requirement 7: リリースワークフロー
**Objective:** As a Monde の保守者, I want タグを push するだけで各 OS 向けのビルド済みバイナリが Release に公開されてほしい, so that 手作業のビルドと添付をせずに、再現性のあるリリースができる

#### Acceptance Criteria
1. When `vX.Y.Z` の形式のタグが push される, the リリースワークフロー shall そのタグのソースから、Windows x64、macOS arm64、macOS x64、Linux x64 の 4 つの対象それぞれについて `monde` の実行ファイルをビルドする。
2. The リリースワークフロー shall 各対象のビルドを、project-foundation が定めた共通のビルド手順をリリース向けの構成（最適化されたビルド）で実行して行う。
3. The リリースワークフロー shall 各対象で、ビルドした実行ファイルが `--version` で期待するバージョンを表示することを確認してからアーカイブを作る。
4. The リリースワークフロー shall 各対象のアーカイブを、GitHub Releases にタグ `vX.Y.Z` の Release として公開し、すべてのアーカイブとチェックサムのファイルを添付する。
5. When タグに対応する Release がまだ存在しない, the リリースワークフロー shall タグ名を題名とする Release を作成して成果物を添付する。
6. When タグに対応する Release（下書きを含む）がすでに存在する, the リリースワークフロー shall その Release に成果物を添付し、人が書いた本文を上書きしない。
7. If 4 つの対象のいずれかでビルドまたは検証が失敗する, then the リリースワークフロー shall Release を公開せず（作成もせず）、失敗した対象と原因がワークフローの実行結果から分かるようにする。
8. If タグから `v` を除いたバージョンと、ソースのビルド構成に書かれたバージョンが一致しない, then the リリースワークフロー shall 不一致を示すメッセージを出して失敗し、Release を公開しない。
9. The リリースワークフロー shall `vX.Y.Z` の形式でないタグの push と、タグを伴わない push では起動しない。
10. The リリースワークフロー shall 手動でも起動でき、その場合はタグ名を入力として受け取り、同じ手順で同じ成果物を作る。
11. The リリースワークフロー shall 同じタグで再実行したときに、同じ内容の成果物（実行ファイルの振る舞いとアーカイブの構成）を再び作れる。
12. The リリースワークフロー shall 継続的インテグレーション（push と pull request で動くビルドとテスト）の定義を変更せず、それとは別のワークフローとして定義する。

### Requirement 8: リリース成果物
**Objective:** As a `monde` を入手する利用者, I want 自分の OS 向けのアーカイブを展開するだけで `monde` が動いてほしい, so that 追加のインストール作業なしにすぐ使える

#### Acceptance Criteria
1. The リリース成果物 shall 各対象について 1 つのアーカイブとし、ファイル名を `monde-X.Y.Z-<os>-<arch>.<ext>` の形式（例: `monde-0.1.0-windows-x64.zip`、`monde-0.1.0-macos-arm64.tar.gz`、`monde-0.1.0-linux-x64.tar.gz`）にする。
2. The リリース成果物 shall Windows 向けを zip、macOS と Linux 向けを tar.gz とする。
3. The リリース成果物 shall 各アーカイブに、実行ファイル（Windows は `monde.exe`、それ以外は `monde`）、`LICENSE`、`README.md` の 3 つを含める。
4. The リリース成果物 shall 各アーカイブを展開したときに、アーカイブ名から拡張子を除いた名前のディレクトリの下に 3 つのファイルが置かれる構成にする。
5. The リリース成果物 shall macOS と Linux 向けの tar.gz で、実行ファイルの実行権限を保持する。
6. The リリース成果物 shall 実行ファイルが外部の実行時ライブラリに依存せず、展開した先で単体で実行できる。
7. The リリース成果物 shall `tests/data/commonmark/spec.txt` とその内容、テストの実行ファイル、テストフレームワーク、ビルドの中間生成物を含めない。
8. The リリース成果物 shall すべてのアーカイブの SHA-256 を `sha256sum` 互換の書式（`<ハッシュ 2 つの空白><ファイル名>` を 1 行ずつ）で列挙した `SHA256SUMS` を 1 つ含める。
9. The リリース成果物 shall `SHA256SUMS` に列挙したハッシュが、添付した各アーカイブのハッシュと一致する。

### Requirement 9: ドキュメントと CLI の整合の検証
**Objective:** As a Monde の保守者, I want ドキュメントが実際の `monde` の振る舞いとずれていないことを確かめたい, so that 利用者がマニュアルどおりに操作して失敗しない

#### Acceptance Criteria
1. The プロジェクト shall README とコマンドリファレンスに載せたサブコマンド名、オプション名、位置引数の個数と順序が、ビルドした `monde` のヘルプの出力と一致することを、リリース前に確認する手順または自動の検査として持つ。
2. The プロジェクト shall README のクイックスタートと翻訳フローの章に書いたコマンド列が、記載どおりに実行して成功することを、リリース前に確認する手順または自動の検査として持つ。
3. When monde-cli の仕様（サブコマンド、オプション、統計の書式、終了コード）が変わる, the プロジェクト shall 対応する README とマニュアルの記述を同じ変更で更新する方針を、保守者向けの手順に示す。
4. The プロジェクト shall README と `docs/` 配下のマニュアルのリポジトリ内リンクが切れていないことを、リリース前に確認する手順または自動の検査として持つ。
