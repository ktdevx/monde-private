## 1. CLI

### Q1-1. サブコマンド体系

**質問:** RFP の 4 つの操作を、どのようなサブコマンドに分けるか。

**回答:** 次の 4 つのサブコマンドに分ける。

| 操作 | コマンド | 入力 → 出力 |
| --- | --- | --- |
| テンプレート生成 | `monde extract` | `.md` → `.pot` |
| 翻訳ファイル作成 | `monde init` | `.pot` → `.po` |
| マージ | `monde update` | `.pot` + `.po` → `.po` |
| 翻訳済み Markdown 生成 | `monde translate` | `.md` + `.po` → `.md` |

### Q1-2. 複数ファイル・ディレクトリの扱い

**質問:** 複数の Markdown ファイルやディレクトリ単位での一括処理は必要か。

**回答:** 初版は 1 ファイル単位の処理のみとする。一括処理はシェルスクリプトなどで行う。

### Q1-3. 設定ファイル

**質問:** コマンドライン引数に加えて、設定ファイルによる実行は必要か。

**回答:** 初版は不要とし、コマンドライン引数のみで指定する。

### Q1-4. メッセージの言語

**質問:** `monde` 自身のヘルプ・エラーメッセージは何語にするか。

**回答:** 英語とする。

## 2. 翻訳単位（メッセージ）

### Q2-1. 分割粒度

**質問:** `.po` の 1 エントリ（msgid）をどの単位にするか。

**回答:** ブロック単位（段落、見出し、リスト項目、表のセル、引用内の段落など）とする。強調・リンク・コードスパンなどのインライン要素は、Markdown 記法のまま msgid に含める。

### Q2-2. 翻訳対象外の要素

**質問:** どの要素を翻訳対象外（原文のまま出力）とするか。

**回答:**

- 翻訳対象外: コードブロック（フェンス・インデント）、HTML ブロック、リンク先 URL、画像 URL
- 翻訳対象: 画像の代替テキスト（alt）

### Q2-3. 同一文の重複

**質問:** 同じ文が文書内に複数回現れた場合、1 つの msgid にまとめるか。

**回答:** gettext の慣例どおり 1 つの msgid にまとめる。出現箇所は参照コメント（`#: file.md:行番号`）で示す。

**補足:** 文脈によって訳し分けが必要な場合があるため、将来、同一文を分けて翻訳できるオプションを追加する可能性がある。

### Q2-4. 翻訳者向けの付加情報

**質問:** 参照コメント以外に、翻訳者向けの情報を出力するか。

**回答:** 要素の種類（見出し、表のセルなど）を `#.` コメントで出力する。

## 3. YAML フロントマター

### Q3-1. 翻訳対象のキー

**質問:** フロントマターのどの値を翻訳対象にするか。

**回答:** オプションで指定したキーのみを翻訳対象とする（例: `--front-matter-keys title,description`）。

**検討した他の案:**

- すべての文字列値を対象にする
- 既定で `title` や `description` などのよく使うキーを対象にし、オプションで変更できるようにする

### Q3-2. 対応する YAML の範囲

**質問:** YAML の仕様のうち、どこまでに対応するか。

**回答:** フロントマターでよく使われる範囲に限定する。

- 対応: マッピング、シーケンス、スカラー（プレーン・引用符付き・ブロックスカラー）、コメント
- 非対応: アンカー、エイリアス、タグ、複数ドキュメント（エラーにするか、そのまま出力する）

## 4. 翻訳済み Markdown の出力

### Q4-1. 原文の書式の再現度

**質問:** 翻訳済み Markdown で、原文の書式をどこまで保つか。

**回答:** 翻訳対象の文字列以外は、原文をバイト単位でそのまま残す（リスト記号、強調記号の種類、空行、インデントなど）。差分レビューやバージョン管理で扱いやすいため。

**検討した他の案:** 構文木から Markdown を再生成する（意味は同じだが、記号や空行が正規化されることがある）。

### Q4-2. 未翻訳・fuzzy エントリの扱い

**質問:** 翻訳が空のエントリや fuzzy のエントリを、出力時にどう扱うか。

**回答:** 未翻訳・fuzzy ともに原文を出力する。fuzzy の翻訳を採用するオプションを用意する。

### Q4-3. 翻訳率による出力の制御

**質問:** 翻訳率が一定未満のときに出力しない、といった制御は必要か。

**回答:** 初版は不要とする。翻訳率の表示（統計）のみ行う。

## 5. PO ファイルとマージ

### Q5-1. マージの方式

**質問:** `monde update` のマージをどのように行うか。

**回答:** GNU gettext の `msgmerge` と同等の動きを目標とする。

- 一致する msgid の翻訳を引き継ぐ
- 似た msgid の翻訳を fuzzy として引き継ぐ（あいまい一致）
- 不要になったエントリは廃止エントリ（`#~`）として残す

### Q5-2. 互換性を確認するツール・プラットフォーム

**質問:** 生成した `.pot` / `.po` の互換性を、どのツールで確認するか。

**回答:** GNU gettext の `msgfmt --check` で検証できることとする。

### Q5-3. 複数形（plural forms）

**質問:** `.po` の複数形エントリの読み書きに対応するか。

**回答:** 読み込み時にエラーにしない程度の対応のみとする。

## 6. Markdown 方言

### Q6-1. GFM の対応範囲

**質問:** GFM のどの拡張に対応するか。

**回答:** 表、タスクリスト、取り消し線、自動リンク（拡張）に対応する。脚注（GFM 仕様外だが GitHub で利用可能）は将来対応とする。

### Q6-2. GFM 以外の方言

**質問:** 将来対応したい方言の候補はあるか。

**回答:** 初版では方言を差し替えられる設計にとどめ、具体的に対応する方言は GFM のみとする。

## 7. 文字コード・プラットフォーム

### Q7-1. 文字コードと改行コード

**質問:** 入出力の文字コードと改行コードをどう扱うか。

**回答:** 入出力は UTF-8 のみとし、BOM 付きのファイルも読み込める。改行コード（LF / CRLF）は入力に合わせて出力する。

### Q7-2. 対応 OS とコンパイラ

**質問:** どの OS とコンパイラに対応するか。

**回答:**

| OS | コンパイラ |
| --- | --- |
| Windows | MSVC、MinGW-w64 |
| macOS | Apple Clang |
| Linux | GCC、Clang |

CI（GitHub Actions）で各環境のビルドとテストを行う。

## 8. 配布・公開

### Q8-1. 配布方法

**質問:** どのように配布するか。

**回答:** GitHub Releases で各 OS 向けのビルド済みバイナリを配布し、ソースからのビルド手順も用意する。パッケージマネージャーへの登録は将来対応とする。

### Q8-2. ライブラリとしての公開

**質問:** Markdown パーサや PO パーサなどの部品を、外部から使えるライブラリとして提供するか。

**回答:** 初版は内部モジュールとする。再利用しやすい設計にはするが、公開 API の互換性は保証しない。

## 9. 品質・計画

### Q9-1. 受け入れ基準

**質問:** 何をもって受け入れとするか。

**回答:** CommonMark 仕様のテストケース（spec.txt）を使い、「extract → translate（翻訳なし）」で原文と同じ出力に戻ること（ラウンドトリップ）を確認する。

### Q9-2. 性能

**質問:** 想定する最大ファイルサイズや処理時間の目安はあるか。

**回答:** 特別な目標は設けない（一般的な文書で体感上すぐ終わればよい）。

### Q9-3. 初版（MVP）の範囲とスケジュール

**質問:** 初版に含める範囲と、目標時期はあるか。

**回答:** 初版は CommonMark + YAML フロントマター + 4 つのサブコマンドとする。GFM 対応は次の版とする。目標時期は未定。
